# OfferPilot 面试包装材料初稿

## 1. 项目一句话介绍

OfferPilot 是一个面向前端求职者的前端面试智能训练平台，围绕题库学习、模拟面试、复盘分析和项目包装，提供一条完整的面试训练闭环。

## 2. 项目背景

我在准备前端求职相关项目时，发现很多练习工具只能覆盖单一场景，比如只做刷题、只做聊天问答，或者只做简历优化，缺少一条从“学习 -> 模拟 -> 复盘 -> 优化表达”的完整链路。

所以我设计并实现了 OfferPilot，希望把前端候选人在面试准备过程中最常见的几个环节串起来：

- 先通过题库做知识学习和筛选
- 再通过模拟面试做真实问答训练
- 然后基于会话内容生成复盘分析
- 最后再把项目经历整理成更适合简历和面试表达的版本

从产品定位上，它更像一个“前端面试训练工作台”，而不是单点功能页面。

## 3. 我的职责（以前端主导视角）

我主要以前端主导的方式推进这个项目，同时也参与了后端接口设计和前后端联调，职责包括：

- 搭建前端工程骨架，完成 Vue 3 + TypeScript + Vite 的项目初始化
- 设计前端页面结构、模块边界，以及 `store + composable + component` 的分层方式
- 独立完成登录、Dashboard、题库、模拟面试、复盘、项目包装、设置页等核心页面
- 设计并接入前端请求层，包括 token 注入、错误处理、接口模块拆分
- 主导 Interview 页面三栏布局和 SSE 流式交互体验设计
- 参与接口契约整理，推动 mock 向真实 API 迁移
- 参与 Review / Project / Interview 等模块的数据结构对齐与联调
- 从前端使用视角推动 LLM / RAG / SSE 协议收口，确保页面能稳定消费实时数据

如果在面试里表达，可以说我是“以前端主导，但对前后端整体链路也有比较完整理解”。

## 6. 5 个技术亮点

### 亮点 1：前端按页面、组件、状态、交互逻辑做了分层设计

我没有把业务逻辑全部堆在页面里，而是把结构拆成：

- `views` 负责页面组织
- `components` 负责区块展示
- `stores` 负责状态收口
- `composables` 负责交互逻辑编排
- `api` 负责接口边界

这样后续从 mock 切到真实接口时，不需要大规模重写页面。

### 亮点 2：Interview 模块使用了 REST + SSE 双通道通信

普通动作例如创建会话、提交回答、结束会话走 REST；模型生成过程走 SSE，前端可以实时接收：

- `state`
- `reference`
- `delta`
- `done`

这样可以更真实地展示面试反馈生成过程，而不是一次性返回整段文本。

### 亮点 3：把题库、模拟面试、复盘分析串成了闭环

这个项目不是孤立页面集合，而是一个训练闭环：

- 题库为 Interview 提供知识来源
- Interview 会生成真实会话数据
- Review 基于真实会话做复盘分析
- Project Polish 进一步服务于候选人的表达优化

这个产品链路本身也是项目设计的亮点。

### 亮点 4：具备 LLM + RAG 的基础能力，而不是纯模板或纯 mock

Interview、Review、Project 三个模块都接入了真实模型能力：

- Interview：结合知识检索做反馈和追问
- Review：基于真实会话消息生成分析
- Project Polish：根据原始材料生成简历版和面试版描述

题库还支持向量化入库，为 RAG 提供知识基础。

### 亮点 5：前端对流式状态、错误状态、空状态做了完整处理

我在页面层面比较重视真实使用体验，例如：

- loading / error / empty 状态分开处理
- 防重复提交
- 防重复 SSE 连接
- 页面切换时清理 transient 状态
- 流式中支持中断和错误提示

这些细节虽然不是“功能点”，但很体现工程完整度。

## 7. 3~5 个技术难点与解决方案

### 难点 1：如何让 Interview 页面支持流式输出，而不是只做普通聊天

#### 问题

如果只用普通请求，用户提交回答后只能等待整段结果返回，体验比较僵硬，也不利于展示“模型正在做什么”。

#### 解决方案

我把通信拆成两部分：

- REST 负责创建会话、提交回答、结束会话
- SSE 负责实时返回 `state / reference / delta / done`

前端再通过 `useSSEStream` 做统一封装，并把事件分发给 `interview store`，让页面只消费状态，不直接操作底层连接。

### 难点 2：如何避免页面逻辑膨胀，尤其是 Interview 这种复杂页面

#### 问题

模拟面试页面同时包含消息列表、输入区、状态区、知识命中区，如果把逻辑都写进一个 `.vue` 文件，会非常难维护。

#### 解决方案

我把它拆成：

- 页面布局层
- 多个功能组件
- `stores/interview.ts`
- `useInterviewSession.ts`
- `useSSEStream.ts`

这样页面只负责组合，复杂逻辑放到 composable 和 store 中，职责更清晰。

### 难点 3：从 mock 迁移到真实 API 时，如何尽量不推翻前端结构

#### 问题

项目前期为了快速搭骨架，用了本地 mock 数据；后期要逐个模块接真实 API，如果前期结构设计不好，切换时会带来大量重写。

#### 解决方案

我在一开始就把页面展示、状态管理、接口层分开：

- mock 先放在 service / store 边界里
- 页面只依赖标准状态结构
- 后续切到真实 API 时主要替换 store 和 api 层

这样实际迁移过程中，页面结构基本保留了下来。

### 难点 4：如何让前端稳定消费真实 RAG 检索结果

#### 问题

后端检索返回的数据更接近知识文档结构，而前端最初是基于较简单的 reference 展示做的。直接对接时字段容易不统一。

#### 解决方案

我对 Interview 的 reference 类型做了统一收口，最终前端标准结构是：

- `questionId`
- `title`
- `category`
- `score`
- `snippet`

store 中做 normalize，组件只消费统一结构。这样即使后端字段有兼容期，页面层也比较稳定。

### 难点 5：如何在工程上兼顾“可演示”和“可继续扩展”

#### 问题

很多项目为了快速展示，容易把逻辑写死，后续很难扩展；但如果一开始就做得太重，又会拖慢开发效率。

#### 解决方案

我的做法是：

- 第一阶段先完成前端壳子和模块规划
- 第二阶段逐步把 mock 切成真实 API
- 第三阶段补 SSE
- 第四阶段接 LLM / RAG
- 最后补文档、环境变量、compose、架构说明

这样项目是分阶段推进的，每一阶段都能运行，同时保留了后续扩展空间。

## 10. 每个追问的简短回答方向

### 1. 你为什么要把前端拆成 store、composable、component 这几层？

回答方向：

因为这个项目页面不只是展示，还有很多交互和异步逻辑。组件只负责 UI，store 负责状态收口，composable 负责交互编排，这样能避免页面文件膨胀，也更方便后期把 mock 切到真实接口。

### 2. 为什么 Interview 用 SSE，而不是 WebSocket 或普通轮询？

回答方向：

这里的核心需求是服务端单向持续输出生成结果，不需要复杂双向实时通信，所以 SSE 更轻量，也更适合增量返回文本。相比轮询，它能实时展示生成过程；相比 WebSocket，接入成本更低，协议也更简单。

### 3. 你这个项目里的 RAG 具体是怎么接起来的？

回答方向：

先把题库 question 做文本拼接并向量化写入 Milvus。Interview 时，会把当前题目和用户回答拼成 query，做相似度检索，拿到相关知识片段后再拼进 prompt 中，让模型基于这些 reference 生成反馈和追问。

### 4. 前端怎么处理流式输出的状态一致性问题？

回答方向：

我把 SSE 事件协议固定成 `state / reference / delta / done`，再由 `useSSEStream` 统一管理连接，由 `interview store` 统一落状态。这样组件层不直接处理连接细节，避免状态散落。还补了重复连接保护、错误清理和手动停止能力。

### 5. 为什么一开始要先做 mock，再逐步替换成真实 API？

回答方向：

因为这个项目模块多、链路长，如果一开始前后端全耦合开发，推进会很慢。先用 mock 把页面结构、状态模型、组件边界搭好，后面接真实接口时只替换 store 和 api 层，效率更高，也更稳。

### 6. Review 和 Project Polish 的生成逻辑有什么区别？

回答方向：

Review 更偏“基于真实面试过程做分析总结”，输入是会话消息和会话上下文；Project Polish 更偏“基于项目原始材料生成更适合求职表达的内容”，输入是项目背景、技术栈、职责和成果。虽然都用统一 LLM service，但 prompt 目标完全不同。

### 7. 你在这个项目里最有挑战的部分是什么？

回答方向：

我觉得是 Interview 模块，因为它同时涉及前端三栏交互、SSE 流式状态、reference 数据消费、REST 与 SSE 协议边界，以及后端的 LLM + RAG 链路，对前后端协同要求最高。

### 8. 如果让你继续迭代，你下一步会优化什么？

回答方向：

我会优先补三件事：

- frontend / backend Dockerfile，完善整套容器化启动
- Redis 的真实接入，比如缓存、会话状态和黑名单
- 更稳定的结构化模型输出校验和异常恢复

### 9. 这个项目里有哪些地方体现了你的工程思维，而不只是页面实现？

回答方向：

我比较重视边界设计和可演进性，比如：前端分层、API 契约整理、mock 到真实 API 的迁移路径、SSE 协议统一、文档补齐、环境变量示例、compose 启动说明。这些都属于工程层面的工作，而不只是把页面写出来。

### 10. 如果后端字段变化了，前端怎么降低改动成本？

回答方向：

前端现在通过 `api + types + store` 这几层收口，尤其像 Interview 的 reference 数据，我在 store 中做了 normalize。这样字段变化时，通常只需要在接口层或 store 层调整，页面组件不一定要跟着改。
